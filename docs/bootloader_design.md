# Bootloader Design Document

## 1. Overview and Role

The bootloader is a small, critical piece of software that runs on device startup. Its primary responsibilities are:

*   **Hardware Initialization:** Initialize essential hardware required for its operation (e.g., clock system, flash interface, minimal GPIOs if needed for status indication or recovery).
*   **Application Integrity Check:** Verify the integrity of the main application firmware stored in flash memory before attempting to boot it. This is typically done by checking a CRC or a cryptographic hash.
*   **Firmware Update Mechanism:**
    *   Detect if a firmware update is requested. This can be triggered by:
        *   A flag set in a shared memory location (e.g., RAM or a dedicated flash sector) by the main application.
        *   A specific GPIO pin state on boot-up (less common for LoRaWAN OTA but useful for recovery).
        *   A message received from the main application via a software interrupt or IPC mechanism if the bootloader has a minimal communication channel (advanced).
    *   If an update is requested and a new firmware image is available in a predefined staging area in flash:
        *   **Verify Firmware Signature:** Perform cryptographic signature verification of the new firmware image. This ensures authenticity and integrity, preventing unauthorized or corrupted firmware from being installed. An ECDSA signature (e.g., using P-256 curve) is recommended.
        *   **Copy New Firmware:** If verification is successful, copy the new firmware from the staging area to the active application region.
        *   **Final Verification:** Optionally, verify the copied image in the application region again.
        *   Clear the update request flag.
*   **Application Launch:** If the application is valid (or after a successful update), the bootloader jumps to the main application's entry point.
*   **Recovery Mode (Optional but Recommended):** If the application is invalid and no valid update can be performed, the bootloader might enter a recovery mode. This could involve:
    *   Signaling an error (e.g., via LED).
    *   Attempting to communicate via a serial port for recovery.
    *   For LoRaWAN, it might try to activate a minimal LoRaWAN stack to report the failure or listen for a recovery command (more complex).

## 2. Memory Layout (Example for STM32WL)

The exact memory map will depend on the specific STM32WL variant's flash size. Below is a conceptual layout:

| Region                      | Start Address (Example) | Size (Example)  | Description                                                                 |
| :-------------------------- | :---------------------- | :-------------- | :-------------------------------------------------------------------------- |
| **Protected Readout (RDP)** | Varies                  | Small           | If STSAFE is not used for root of trust, public key for bootloader update might be here. |
| **Bootloader**              | `0x08000000` (Start of Flash) | 32 KB - 64 KB   | Bootloader code. Should be write-protected after initial programming.      |
| **Application Metadata**    | End of Bootloader       | 1 KB - 4 KB     | Stores version, size, CRC/hash of the current valid application.            |
| **Application Image**       | End of App. Metadata    | e.g., 128 KB - 192 KB | Main firmware.                                                              |
| **Firmware Staging Area**   | End of Application      | e.g., 128 KB - 192 KB | Area where new firmware is downloaded before being copied to Application. Size should match or exceed Application Image size. |
| **Device Configuration**    | End of Staging Area     | 4 KB - 8KB      | Non-volatile configuration data (LoRaWAN keys if not in STSAFE, app settings). |
| **Shared RAM (Bootloader <-> App)** | Top of RAM      | Small (e.g. 32 bytes) | For passing update flags or simple messages.                               |

*   **Note:** Sizes are indicative. The bootloader should be as small as possible while being robust. The Staging Area must be large enough to hold a complete firmware image.

## 3. Cryptographic Signature Verification

Ensuring the authenticity and integrity of firmware updates is paramount.

*   **Algorithm:** ECDSA with NIST P-256 curve is recommended. SHA256 should be used as the hashing algorithm.
*   **Keys:**
    *   **Private Key:** Securely stored by the entity responsible for signing firmware updates (e.g., build server, dedicated signing machine). **This key MUST NOT be on the device.**
    *   **Public Key:** Embedded within the bootloader code itself or stored in a write-once, read-only memory region of the MCU if available and STSAFE is not the root of trust for this. If STSAFE is used, it can securely store the public key or a root certificate and perform the verification.
*   **Process:**
    1.  The firmware image is generated by the build system.
    2.  The firmware image (or its hash) is signed using the private ECDSA key, producing a signature.
    3.  The signature is appended to the firmware image or delivered alongside it.
    4.  When the device's bootloader receives a new firmware image and its signature:
        a.  It calculates the SHA256 hash of the received firmware image.
        b.  It uses the embedded public key to verify the received signature against the calculated hash.
        c.  If the signature is valid, the firmware is considered authentic and intact.
        d.  If verification fails, the firmware image is rejected, and the update process is aborted.

## 4. Update Process Flow

1.  Main application receives an update notification (e.g., via LoRaWAN downlink).
2.  Main application downloads the new firmware image (with its signature) into the **Firmware Staging Area**. This download will likely happen in chunks. Integrity of each chunk (e.g. CRC) and then the full image (e.g. SHA256) should be checked by the application.
3.  Once the download is complete and the application has verified the integrity of the downloaded image (e.g., by checking a hash provided with the image against the calculated hash of the image in the staging area), the application sets an "update request flag" (e.g., in shared RAM or a dedicated flash location).
4.  The application then triggers a system reset.
5.  On startup, the bootloader runs.
6.  The bootloader checks the "update request flag".
7.  If the flag is set:
    a.  The bootloader locates the new firmware image in the **Firmware Staging Area**.
    b.  It performs the ECDSA signature verification as described in section 3.
    c.  If signature verification is successful:
        i.  The bootloader erases the **Application Image** region.
        ii. The bootloader copies the new firmware from the **Firmware Staging Area** to the **Application Image** region.
        iii.The bootloader updates the **Application Metadata** (version, size, hash/CRC) for the new application.
        iv. The bootloader clears the "update request flag".
        v.  The bootloader may perform a self-reset to ensure a clean start or directly jump to the new application.
    d.  If signature verification fails:
        i.  The bootloader clears the "update request flag".
        ii. It may log the error or increment a failed update counter.
        iii.It proceeds to boot the existing (old) application if it's still valid. If not, it enters a recovery state.
8.  If the "update request flag" is not set, the bootloader verifies the integrity of the existing application in the **Application Image** region (using data from **Application Metadata**).
9.  If the existing application is valid, the bootloader jumps to its entry point.
10. If the existing application is invalid, the bootloader enters a recovery state.

This outline provides a foundation for the bootloader's design. Specific implementation details will depend on the chosen STM32WL SDK, flash drivers, and cryptographic libraries.
