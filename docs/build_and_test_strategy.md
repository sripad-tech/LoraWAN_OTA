# Build System and Basic Test Structure

This document outlines the build system approach and the initial structure for testing the CPV Field Logger firmware.

## 1. Build System / IDE

*   **Primary Choice: STM32CubeIDE**
    *   **Rationale:** STM32CubeIDE is STMicroelectronics' official integrated development environment. It provides a comprehensive environment for STM32 development, including project configuration (via `.ioc` file for CubeMX), code editing, building (GCC compiler toolchain), debugging, and programming. It seamlessly integrates with STM32CubeMX for hardware abstraction layer (HAL) and middleware configuration (like I-CUBE-LRWAN).
    *   **Build Process:** The build process will utilize the managed build features of STM32CubeIDE, which internally uses `make` and `GCC`.
*   **Alternative (for CI/CD or advanced users): CMake with ARM GCC**
    *   **Rationale:** For automated builds, continuous integration (CI), or users preferring a more command-line oriented approach, a CMake-based build system could be set up. CMake allows for more flexible build configurations and is widely supported.
    *   **Initial Focus:** The project will initially focus on STM32CubeIDE. A CMake setup can be added later if needed.

## 2. Unit Testing

*   **Importance:** Unit tests are crucial for verifying the correctness of individual firmware modules (e.g., data packer, sensor interface logic, parts of the OTA handler) in isolation.
*   **Framework: Ceedling (Unity + CMock)**
    *   **Rationale:** Ceedling is a build system for C projects that integrates the Unity testing framework (for writing test cases) and CMock (for generating mocks and stubs). This allows for effective testing of C modules by isolating them from their dependencies.
    *   **Features:**
        *   Test discovery.
        *   Mock generation for dependencies.
        *   Easy test execution and reporting.
*   **Host-Based Testing:** Unit tests will primarily be compiled and run on the host machine (developer's PC), not on the target STM32 hardware. This allows for faster execution and easier debugging of tests.
*   **Test Structure:**
    *   A `tests/unit/` directory will be created at the root of the project.
    *   For each module `src/foo/bar.c`, a corresponding test file `tests/unit/test_bar.c` will be created.
    *   Mocks will be generated by Ceedling for dependencies of the module under test.

## 4. Integration Testing

*   **Purpose:** Integration tests verify the interaction between different modules of the firmware running on the actual STM32 hardware.
*   **Approach:**
    *   These tests will involve deploying firmware to a development board and observing its behavior, potentially using a debugger, serial output, or by monitoring LoRaWAN messages on a network server.
    *   Test cases will focus on end-to-end scenarios (e.g., read sensor -> package data -> transmit LoRaWAN -> verify on server).
*   **Structure:** A `tests/integration/` directory can be used to store test plans, scripts, or specialized test firmware.
*   **Initial Focus:** While crucial, extensive integration testing will follow the initial development and unit testing of core modules. The initial setup will focus on establishing the unit testing framework.

## 5. Continuous Integration (CI) - Future Goal

*   Once a robust set of unit tests is available, a CI pipeline (e.g., using GitHub Actions, Jenkins) can be set up to:
    *   Automatically build the firmware.
    *   Run all unit tests on each commit.
    *   Report build and test status.

This strategy aims to establish a solid foundation for building and testing the firmware, starting with STM32CubeIDE for development and Ceedling for host-based unit tests.
